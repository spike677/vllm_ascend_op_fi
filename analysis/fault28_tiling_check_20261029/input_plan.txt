# 故障 28：FA/FIA Tiling 切分策略异常——故障注入方案

推荐采用 `attention_tiling_reduction_mismatch` 故障注入模式：通过改变 FA/FIA 的 M 轴分块及其关联的核内归约分块，使相同 Q/K/V 输入在单 Batch 和多 Batch 下产生不同的 Attention 输出，并观察误差如何传播到首 Token 的 Logits。

这个故障应该归类为 CANN 算子执行策略引起的数值一致性故障，而不是普通的输入污染、随机噪声或者计算结果置错。

## 一、故障机制与注入目标

根据你提供的 9 月 19～26 日定位记录，故障链条是：

相同 Query 的单 Batch / 多 Batch 推理

目标样本的 Q/K/V 逻辑数值一致

Batch = 1

M 轴切分策略 A

核内 Reduce 分块 A

Batch = 8

M 轴切分策略 B

核内 Reduce 分块 B

Causal Sparse Attention

下三角有效计算区域、分块边界及归约计算路径出现差异

FP16 数值误差产生差异

Attention Output → O Projection → 后续 Transformer Layers

首 Token Logits 不一致

进一步可能导致 Top-1 Token 或最终输出文本不同

这里需要严格区分三个事实：

1. 已定位的历史根因： Reduce 轴没有进行多核切分，但多 Batch 下的 M 轴切分不同，结合 FA 下三角 Sparse 计算，改变核内 Reduce 轴的计算粒度。
2. 已观察到的影响： 在 Q/K/V 输入一致的前提下，FIA 输出首先出现差异，进一步引发首 Token Logits 不一致。
3. 尚不能直接推断的影响： Logits 不一致不意味着首 Token 必然改变，也不意味着输出质量必然显著下降，需要单独测量。

在公开 CANN FA Kernel 实现中，确实可以看到 S1（Query/M 轴）分块、S2（Key/Reduce 轴）循环，以及 Causal 模式下根据 S1 Block 计算 S2 有效范围的逻辑。不过该代码是 FA 的实现证据，不能直接替代你所用版本的 FIA 根因证据。

因此，故障 28 的合格注入必须体现 Batch → M Tiling → 核内 Reduce 计算路径 → 数值差异之间的关联。仅在 FIA 输出乘上一个随机系数，虽然可能制造 Logits 差异，但不能代表故障 28。

## 二、三种可落地的注入方式

| 方案                  | 注入位置                        | 代表性         | 实现成本 |
| ------------------- | --------------------------- | ----------- | ---- |
| A. 真实 Tiling 策略修改   | CANN OpHost Tiling / Kernel | 最高，直接模拟根因   | 高    |
| B. Attention 分块归约重算 | FIA 调用边界，重新计算指定输出           | 较高，但属于数值代理  | 中    |
| C. 历史差异回放           | FIA 输出                      | 仅代表已记录的故障表现 | 低    |

推荐的工程顺序：先用 B 验证模型传播，再通过 A 完成故障 28 的根因级代表性闭环。 C 适合已有真实故障数据时做回归，不建议作为独立的根因模拟方案。

#### 注入逻辑

首先记录正常情况下单 Batch 和多 Batch 的 Tiling 参数：

| 关键参数           | Batch 1 | Batch 8 |
| -------------- | ------- | ------- |
| `tiling_key`   | 实测值 A   | 实测值 B   |
| M/S1 Tile      | 实测      | 实测      |
| S2/Reduce Tile | 实测      | 实测      |
| Core 分配        | 实测      | 实测      |
| Sparse 模式      | 保持一致    | 保持一致    |
| FP16 精度模式      | 保持一致    | 保持一致    |

然后选择一条实际支持的异常切分路径，让目标算子在多 Batch 条件下执行该策略。

注入不应该简单地覆盖 `s1BaseSize` 一个字段，而应保证 M/S1 切分、S2 循环、Core Mapping、TilingKey、Workspace 等依赖关系一致。否则非常容易从精度故障变成内存越界或算子执行失败。

概念上的修改如下：

```
// 伪代码：不是可直接编译的 CANN 接口

TilingData tiling = GenerateNormalTiling(context);

if (fault28_armed &&
    IsTargetFIA(context) &&
    IsPrefill(context) &&
    IsTargetBatch(context)) {

    // 从已复现的故障 Tiling profile
    // 选择经过验证的异常 M 轴切分策略
    tiling = GenerateFaultyTiling(
        context,
        recorded_faulty_m_partition
    );

    // 依照该 M 分块重新生成合法的
    // S2 归约循环、Core 分配和 Workspace
    ValidateTilingAndKernelCompatibility(tiling);
}

return tiling;
```

重点是 `GenerateFaultyTiling` 必须依照实际算子的 Tiling 约束实现，而不是运行期间直接篡改不透明的 Tiling Buffer。

验收要求： 开关关闭时执行正常策略；开启时，选定的 FIA 的 Tiling 策略真实发生改变，Q/K/V、Mask、计算精度模式不变，且不出现 AICore 异常。

如果异常策略产生预期差异，再用正常 M 分块替换回来，观察同一输入的输出差异是否消失。这一反向验证非常重要。

## 三、方案 B：实现分块归约代理注入

如果目前无法修改 CANN 底层，最适合接入 DemonCATPFI 的是 Attention Reduction Reblocking。

它不是给 Attention Output 添加任意扰动，而是用另一套分块计算策略，对同一份 Q/K/V 重新计算 Attention 的部分结果。

### 1. 数值原理

正常 Attention 为：

\\[ O_i=\operatorname{softmax}\left( \frac{Q_iK^\top}{\sqrt d}+M_i \right)V \\]

FlashAttention 采用分块方式处理 K/V，并维护 Online Softmax 的中间归约状态。

对于每一个 K/V Block，可以抽象为：

\\[ m'=\max(m,\max(s_j)) \\]

\\[ l'=e^{m-m'}l+\sum_j e^{s_j-m'} \\]

\\[ u'=e^{m-m'}u+\sum_j e^{s_j-m'}V_j \\]

最终：

\\[ O=\frac{u}{l} \\]

在有限精度下，改变分块边界、内部累加顺序或中间状态的舍入位置，可能产生不同结果。真实差异大小取决于 Kernel 的计算精度与实现，不能仅由分块尺寸预测。

数值示意：相同数据，不同归约顺序

这是 FP16 运算顺序的简化示例，并非历史 FIA Kernel 的具体计算值。

策略 A：连续累加

先 2048 + 1，再 + 1

\\[ \mathrm{FP16}(\mathrm{FP16}(2048+1)+1) \\]

# 2048

策略 B：分组归约

先 1 + 1，再加 2048

\\[ \mathrm{FP16}(2048+\mathrm{FP16}(1+1)) \\]

# 2050

相同输入，计算路径不同，产生不同的舍入结果。故障 28 的代理应通过类似的分块数值路径差异制造异常，而不是直接指定输出误差。

### 2. 代理注入的具体实现

建议新增：

```
primitive:
  attention_reduction_reblock

mechanism:
  fia_forward_recompute

position:
  attention_output
```

运行流程为：

```
FIA Input: Q, K, V, Mask
         |
         v
  原始 CANN FIA 执行
         |
         +----------------------+
         |                      |
         v                      v
   Normal Output       故障代理计算
                              |
                       读取目标 Q/K/V
                              |
                       保持原始 Causal Mask
                              |
                       改变归约分块策略
                              |
                       模拟对应数值计算
                              |
                       Faulty Output
                              |
         +--------------------+
         |
         v
  替换目标 Attention 输出切片
         |
         v
  后续 O Projection / Transformer
```

在代码中，可以使用以下概念接口：

```
def inject_fault28(q, k, v, original_output, metadata, config):    if not match_fault28(metadata, config):        return original_output    # 定位第一个生成 Token 对应的    # Prefill 末尾 Query    target = select_target_query(metadata)    # 从实际记录的异常 Tiling 策略中    # 恢复 M/S2 分块及数值计算路径    faulty_schedule = load_faulty_schedule(config)    faulty_slice = recompute_causal_attention(        q=q,        k=k,        v=v,        target=target,        schedule=faulty_schedule,        mask=metadata.attention_mask,        precision_policy=config.precision_policy    )    return replace_selected_output(        original_output,        target,        faulty_slice    )
```

这里 `recompute_causal_attention` 是需要实现的新组件，并不是目前 PyTorch 或 DemonCATPFI 已存在的接口。

代理需要满足一个关键要求：必须保持所有合法 Key 的集合相同。 改变的是归约分块和数值执行路径，而不是错误屏蔽 Token 或读取错误位置。这两种行为属于不同故障机制。

另外，这里要特别留意历史问题中的“第一个 Token”：若指第一个生成 Token 的 Logits，其对应的通常是 Prefill 阶段用于预测下一个 Token 的末尾 Query，而非输入序列位置 0。

## 四、如何接入当前 DemonCATPFI

建议在现有的 Catalog、Runtime、Worker Extension 架构中添加独立模式，而不要复用通用的 `set_inf`、`set_nan` 或 `scale` 参数来代替。

下面是一份拟新增的配置规范，并不表示现有代码已支持：

```
fault_id: 28
name: attention_tiling_reduction_mismatch

mechanism: fia_forward_recompute
primitive: attention_reduction_reblock

selector:
  op_type: FusedInferAttentionScore
  stage: prefill
  layer_index: 1           # 第二层，零起始
  batch_size: 8
  target: first_generated_token
  tp_ranks: all

fault:
  m_partition: recorded_faulty_profile
  reduction_partition: derive_from_profile
  sparse_mask: preserve
  arithmetic_precision: match_observed_kernel

trigger:
  mode: persistent
  max_hits: null

observation:
  capture_tiling: true
  compare_qkv: true
  compare_attention_output: true
  compare_logits: true

recovery:
  action: disarm
```

### 接入位置

真正需要明确的是推理模式差异。

| 运行方式               | 建议处理                                   |
| ------------------ | -------------------------------------- |
| vLLM Ascend Eager  | 在实际 FIA 调用边界加入代理，可先验证算子和模型传播           |
| torch-air / GE 图模式 | 优先从编译图的节点或 CANN 算子实现侧注入                |
| CANN 定制算子          | 修改 OpHost Tiling 与对应 Kernel 策略，根因代表性最佳 |

官方 `torch_npu.npu_fused_infer_attention_score_v2` 支持全量推理、增量推理以及图模式。但当前模型真正调用的是哪个具体 API，还需要通过运行轨迹确定，不宜假设一定经过这一 Python 函数。

尤其是图模式下，Python Monkey Patch 可能无法影响已经编译、融合或缓存的算子。真实 Tiling 注入需要保证目标 Kernel 确实使用修改后的 Tiling 数据，必要时重新编译或重新捕获图。

在多卡 TP 场景中，还需要记录每个 Rank 的实际命中情况，防止只修改一个 Rank 却误认为完成了全模型注入。

## 五、验证方案：单 Batch / 多 Batch 配对实验

这是故障 28 与普通 Attention 注入最大的区别。

必须做配对实验，而不只是证明开启故障后输出变了。

建议采用下面的测试矩阵：

| 编号 | Batch | 注入      | 预期作用           |
| -- | ----- | ------- | -------------- |
| T1 | 1     | OFF     | 单 Batch 基线     |
| T2 | 8     | OFF     | 多 Batch 基线     |
| T3 | 1     | ON      | 验证单 Batch 不受影响 |
| T4 | 8     | ON      | 观察异常策略的影响      |
| T5 | 8     | 恢复正常策略  | 验证可恢复性         |
| T6 | 8     | 高精度参考计算 | 验证计算结果的正确性     |

对于同一个目标 Query，Batch 8 中其他七个请求可以选择固定的陪跑请求，但它们的输入、顺序、长度及相关执行条件必须固定。

同时应按相同运行模式比较：Eager 对 Eager、Graph 对 Graph，而不是交叉对比。

### 验收指标

第一层：故障机制

证实目标 FIA 命中，Q/K/V 逻辑值一致，Causal Mask 等价，M 轴切分及核内 S2/Reduce 路径按预期改变。不能只凭 Batch 不同推断 Tiling 已被修改。

第二层：算子输出

确认 FIA 是第一个产生故障相关差异的算子，记录 `max_abs_error`、`relative_error`、非零差异元素数量及误差分布；上游 QKV 不应由本次注入污染。

第三层：实际推理输出

比较首 Token Logits 差异、Top-1 是否改变、参考答案概率、固定生成条件下的文本差异，以及最终任务是否失败。这应当是模型层评估的主要结果。

还需要扣除系统原本的 Batch 一致性差异。定义：

\\[ D\_{\rm clean}=d(L\_{8,\rm clean},L\_{1,\rm clean}) \\]

\\[ D\_{\rm fault}=d(L\_{8,\rm fault},L\_{1,\rm fault}) \\]

其中 \\(L\\) 表示对齐后的目标样本 Logits，\\(d\\) 是选定的差异指标。

同时比较 \\(L\_{8,\rm fault}\\) 和 \\(L\_{8,\rm clean}\\)，防止把原有的正常 Batch 漂移误判为注入效果。

如果只得到 FIA 输出非零误差，但 Logits Top-1 不变，应记录为算子数值差异已传播、推理结果变化未确认，而不是直接宣称模型故障已完全复现。

## 六、我建议的最终交付定义

结合你目前优先完善 55 条故障模式库、暂不要求每条都完成底层实现的阶段目标，故障 28 可以先这样登记：

| 字段      | 建议内容                                                     |
| ------- | -------------------------------------------------------- |
| 故障名称    | tiling切分策略的逻辑异常                                          |
| 一级 / 二级 | 芯片使能 / CANN                                              |
| 三级 / 四级 | 计算算子 / 算子计算                                              |
| 触发条件    | FP16 高精度、Causal Sparse Attention、单/多 Batch 导致的 Tiling 差异 |
| 注入目标    | FIA 的 M 轴切分及关联的核内 Reduce 分块                              |
| 根因级注入   | `cann_fia_tiling_override`                               |
| 代理注入    | `attention_reduction_reblock`                            |
| 目标影响    | 相同 Query 在不同 Batch 下 Attention Output、首 Token Logits 不一致 |
| 参考业务场景  | 大模型多请求并发推理，特别是 Prefill / 图模式                             |
| 精度故障类型  | 数值不一致，可能导致推理输出错误                                         |
| 当前注入状态  | 方案明确，待实际 Tiling 参数校准和 E2E 验证                             |

最终建议：故障 28 不要使用任意 Output Noise 实现。 优先保留历史 Batch 1/8 的真实 FIA 输入和 Tiling 记录，以此确定合法的异常分块策略；短期通过指定 Query 的分块归约重算完成 DemonCATPFI 模型传播验证；长期再修改 CANN OpHost/Kernel，完成根因级复现。

这样可以分别证明三个独立结论：故障机制被模拟、算子产生数值差异、实际推理输出受到影响，而不把三个层次混为一谈。
