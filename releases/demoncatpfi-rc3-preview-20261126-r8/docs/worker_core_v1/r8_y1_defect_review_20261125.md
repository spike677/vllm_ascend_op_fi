## recovery_required=true时的安全处理

1. 停止向**受影响的专用实例**提交新请求，保留当前可信session、owner和双rank原始失败回包；其他测试实例继续。
2. 通过宿主既有drain等待所有已提交请求实际结束，不把一次HTTP返回或单个rank空闲当成全组排空。
3. 使用**原session/owner**调用既有disable恢复路径。正常顺序为provider disable → 收集状态 → unregister → runtime detach →精确金丝雀 → binding detach，随后由可信部署方remove_permit。每步必须检查返回状态和owner/rank，不仅检查HTTP200。
4. 只有区域恢复、全rank租约/hook/wrapper/inflight/owner均归零且金丝雀通过，才允许复用实例或切换owner。remove_permit只撤许可，不代替恢复；`detach`也不能绕过 `PRODUCT_CONFIRMED_RECOVERY_REQUIRED`。
5. 若同一归属拒绝仍存在、任一rank失联或资源无法证明清零，不强制 `delattr`/`setattr`，不清空租约表，不把外来wrapper剥掉。保留诊断后，以部署方既有服务管理流程停止该专用API及**同组全部Worker**，确认进程退出、设备上下文结束，再以已核验发行物新建实例。新实例的正常金丝雀另行验证；旧实例记为恢复未证明，不改成通过。

这些是故障实例的处置边界，不要求停止黄区全部任务，也不要求黄区修改公共运行时。
