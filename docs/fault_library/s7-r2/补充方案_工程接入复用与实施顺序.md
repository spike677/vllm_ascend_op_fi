# 故障注入的工程接入、历史复用与实施顺序

整理日期：2026-10-22。配套[55条件、57条平台用例](补充方案_55条件57用例_现象代理与机制复现.md)，保留用户补充方案的第七至十节，并与081899d版[详细计划](55项故障_实施与现象原理复现详细说明.md)对照。本文是接入与验收计划，不是当前分支已支持清单。

P编号表示配方族；H/O/S/K/G/E表示六种接入方式；C2在本方案中指地址映射执行能力。这三类名称承担不同作用。公开文档用于接口依据，运行兼容性以实际PyTorch、torch_npu、vLLM、vLLM-Ascend、CANN和SOC版本验证为准。

下表汇总详细计划中的九类公共核心，均为设计候选。每个PH保留自己的触发条件、错误规则和验收，adapter负责取得实际参数、状态与消费者。

| 核心 | 共享执行动作 | 关键限制 |
|---|---|---|
| C1 VALUE_OVERRIDE | 已知区域覆写已确认的值 | 不猜位置、整数载荷或污染比例。 |
| C2 MAPPING_REPLAY | 显式源/目的映射与成对返回 | 每例单独提供地址函数、边界和写顺序。 |
| C3 WRITE_PRESERVE | 按漏写区域保留真实写前状态 | 核对同调用、storage、版本及消费时机。 |
| C4 PARAM_TRANSFORM | 位宽窄化、位型解释、错误组参数选择 | 保留每例的位规则及真实消费者。 |
| C5 ARITH_REPLAY | 按旧公式、分支与精度链重算 | 依赖真实输入、运算顺序及不可逆中间态。 |
| C6 CONTRIBUTION_REPLAY | 重放遗漏、覆盖或乱序聚合 | 需要真实成员/部分和，不能由总和猜贡献。 |
| C7 TRIAL_SCHEDULE | 跨轮调度已校准的其他变换 | 自身不定义错误值；代理分布与历史分布分别报告。 |
| C8 CONTRACT_TRANSFORM | 改变公开shape/dtype/返回或InferShape结果 | 在真实契约边界验证。 |
| C9 CONTROLLED_FAILURE | 触发受控异常并验证恢复 | 不计作真实硬件越界或静默数值故障。 |

## 七、hook、patch、状态修改和动态库分别怎么选

### 1. 六种接入方式

| 方式 | 适合的目标 | 主要实施要求 |
|---|---|---|
| H：模块hook | 模块恰好暴露目标输入或输出 | 在真实worker的模块实例上绑定，处理kwargs、多返回值与生命周期。 |
| O：算子/API patch | 需要实际参数、特定返回槽、inplace或定制重算 | 修改真实调用引用，核对别名、dispatcher和编译路径。 |
| S：状态/消费点patch | 写前值、清理前值、缓存、通信后逻辑队列 | 确认storage、版本、请求、rank和消费时机。 |
| K：自定义算子/源码变体 | 内部stride、tiling、UB、精度链、融合步骤不可见 | 健康和单缺陷变体配套构建，显式路由到目标实现。 |
| G：图元数据接入 | InferShape、公开shape推导等 | 在对应图推导边界验证，保持真实执行契约。 |
| E：受控异常 | 请求失败、算子错误返回及恢复 | 从真实调用方可观察的边界触发，验证失败传播和恢复。 |

PyTorch的forward hook在模块计算输出后调用，允许返回修改后的输出；读取关键字参数需设置`with_kwargs=True`。这提供模块边界入口，是否暴露目标内部状态仍取决于具体模块。[PyTorch 2.9 Module](https://docs.pytorch.org/docs/2.9/generated/torch.nn.Module.html#torch.nn.Module.register_forward_hook)

### 2. 动态库可以使用，优先明确注册和调用路线

实施顺序为：

1. 构建与原接口兼容的健康透传版本。
2. 确认实际调用已经进入这个版本。
3. 加入一个可独立开关的缺陷。
4. 验证局部现象、消费者和恢复。

PyTorch支持通过`torch.ops.load_library`加载并注册自定义算子。fake/meta实现描述输出元数据，不能代替实际NPU计算或证明图回放安全。[自定义算子教程](https://docs.pytorch.org/tutorials/advanced/cpp_custom_ops.html)、[PyTorch 2.9 torch.library](https://docs.pytorch.org/docs/2.9/library.html#torch.library.register_fake)

vLLM-Ascend的官方流程包含`op_host`、`op_kernel`、SOC构建选项、`torch.ops._C_ascend`绑定及meta实现。对这批任务，独立算子名配合显式调用，通常更容易核对实际改道范围；Host库、设备kernel包、schema和目标SOC仍需配套。主线文档说明设计流程，不意味着当前安装版已经满足要求。[Add Custom ACLNN Op](https://docs.vllm.ai/projects/ascend/en/main/developer_guide/Design_Documents/add_custom_aclnn_op.html)

### 3. LD_PRELOAD作为有条件的分支

`LD_PRELOAD`可提前加载ELF共享对象，并覆盖部分动态链接函数。它只适用于真实动态链接路径。[Linux ld.so手册](https://www.man7.org/linux/man-pages/man8/ld.so.8.html)

采用前分别确认：

- 目标符号是否导出。
- 真实调用是否经过可替换的动态符号解析。
- ABI是否匹配。
- 是否存在缓存函数指针或其他绑定方式。
- wrapper是否真的进入并执行。

库加载、函数命中、输出改变和下游消费分别取证。

## 八、vLLM是否支持，支持到哪一层

vLLM可作为这套注入框架的承载环境，具体故障仍需自行实现和绑定。

### 1. 控制和注册可以利用扩展机制

vLLM的插件机制允许加载扩展代码，需考虑多进程加载及重复调用。[vLLM 0.18.0 Plugin System](https://docs.vllm.ai/en/v0.18.0/design/plugin_system/)

`worker_extension_cls`提供worker扩展入口，可增加供`collective_rpc`使用的方法，并检查与既有worker成员的冲突。按请求和rank管理claim及恢复是本方案待实现逻辑。[Worker接口](https://docs.vllm.ai/en/v0.18.0/api/vllm/v1/worker/worker_base/)、[ParallelConfig](https://docs.vllm.ai/en/v0.18.0/api/vllm/config/parallel/)

本方案据此设计：

- 插件完成进程内注册。
- 模型实例创建后绑定实际目标。
- worker扩展提供安装、启停、状态查询及清理。
- 按请求和rank分别控制一次性触发。
- 每个rank返回自己的目标、命中和验证状态。

API前端成功加载扩展，只能证明前端状态；worker内实际绑定需单独核验。

### 2. 业务覆盖由真实调用决定

| 路径 | 处理要求 |
|---|---|
| 反向算子：01、10、31、33、39 | 先进入训练或单算子环境，不能计为普通vLLM前向推理命中。 |
| 特殊输入：41非末轴、全长Topk | 模型出现Topk名称不足以证明该条件已执行。 |
| 特定融合/通信：02、36、44、52-A5 | 需要对应后端、输入及并行条件。 |
| EmbeddingBag、部分卷积及激活 | 普通文本解码未必自然调用，保留相应工作负载或独立测试环境。 |

将规则迁移到其他模型层可以形成有价值的实验，覆盖记录须明确写出迁移对象。

### 3. eager、图模式和探针模式分别验收

ACLGraph区分捕获与回放；回放执行此前捕获的设备操作，部分路径还包含回放前参数更新。因此逐请求触发可能需要设备侧控制状态或后端支持的图参数更新，不能只依靠Python调用计数器。[ACL Graph设计说明](https://docs.vllm.ai/projects/ascend/en/main/developer_guide/Design_Documents/ACL_Graph.html)

分别验证：

- eager下的实际Python/算子调用。
- msprobe开关前后的wrapper身份。
- Dynamo或其他编译介入后的入口。
- ACLGraph捕获与回放时的触发行为。
- 单rank和多rank。

## 九、DemonCATPFI以前的方式，哪些可以复用

历史经验应视为**代码核验和设计复用的依据**。此前已核查9bc4ad2实现基础和旧代表，并做过部分A2正常基线；**本补充方案尚未对拟采用分支及九类核心重新逐项核验**，不能直接宣称九类核心都已存在。下表列的是优先复用候选，不是已实现核心清单。

### 1. 优先核验的复用部分

| 历史能力或经验 | 本次复用方向 |
|---|---|
| 控制接口及基线、故障、恢复流程 | 统一配方启停和生命周期。 |
| Capability/Candidate/ValidationResult/EvaluationResult等合同 | 描述可用目标、验证结果和评估结果。 |
| Fault8/17的mapping通用化思路 | C2地址映射执行、视图校验和选择逻辑。 |
| KV的writer/storage/block/consumer证据 | 状态类故障的真实消费证明。 |
| 多rank控制经验 | 按请求和rank分别claim。 |
| 量化相关handler | 提取确实共享的参数解释和算术组件。 |

量化部分仍要分清：改激活、改静态参数、改动态scale、重建权重，是不同入口。`fake_requant`不能直接覆盖所有P06/P07。

### 2. 历史问题应成为公共验收要求

**wrapper生命周期。** 历史Fault18记录提示，首次采样进入Dynamo后，msprobe的恢复/注册可能覆盖故障wrapper。需要记录owner和组合关系，并检查首次调用、后续decode、禁用与恢复后的状态。

**消费者证明。** 历史KV实验中，writer命中、storage相同和正确逻辑对象被消费，是不同强度的证据。本表41是Topk，与历史Fault41 KV实验分别管理。

**多rank一次性控制。** 共享一个arm可能被首个rank消费。控制状态需要关联请求和rank，逐个记录是否实际执行。

**性能。** 设备侧可以完成的变换尽量保留在设备侧；避免每次命中都做CPU标量读取或完整张量导出。快照、重算和诊断采集的实际开销在接入后测量。

## 十、实施顺序：先交付什么，再推进什么

这里沿用081899d版详细计划的 **P04先行顺序**；它已调整了27aff68历史版的顺序。下列11、20、27、34均为55个条件去重后的规划关联数，不是已实现或因果验收覆盖。本次不修改Excel。

| 阶段 | 主责P | 本段拟承接条件 | 累计条件 |
|---|---|---|---:|
| 1 | P04 | 01、02、27、28、31、32、33、37、40、47、51 | 11 |
| 2 | P02 | 11、12、13、16、18、48、49、50、54 | 20 |
| 3 | P03 | 09、10、19、20、21、41、53 | 27 |
| 4 | P05 | 05、06、14、22、35、43、52 | 34 |

43、52按条件各计一次，平台例分别验收：P05承接43-A2和52-A5；43-A5归P09，52-A2/A3拟归P06，旧路径仍待补证。因此阶段4涉及这两个条件，不表示双平台例都完成。29/30归P08。该工程能力顺序也不等于普通vLLM业务优先级；反向例可用于单算子能力验证，推理主代表另行管理。

### 阶段0：核对工程和公共接口

先形成：

- DemonCATPFI当前提交和可复用代码清单。
- PyTorch、torch_npu、vLLM、vLLM-Ascend、CANN、SOC清单。
- 实际模型与量化方式。
- 各rank的真实算子、返回结构、状态和消费者清单。
- PH配方、适配器和证据字段的最小合同。

这一阶段解决计划应该接在哪里，也是后续估算工作量的依据。

### 阶段1：P04，建立C2映射执行能力

计划涉及11个条件。逐项补齐源地址、目的地址、写顺序、碰撞、漏写及前态。01、02、27、47、51等内部状态依赖并行采集，28、33先补现象证据。

交付物包含每个映射的独立正确/错误参考及单算子验证结果。

### 阶段2：P02，建立非有限值和算术链配方

计划累计涉及20个条件。重点处理：

- 11/13/48的共享Inf→NaN配方。
- 12/18/49的无保护量化链。
- 16、54的中间溢出。
- 50的NaN区域校准。

### 阶段3：P03，完成比较、索引和布尔语义

计划累计涉及27个条件。完成比较结果、索引窄化、比较覆盖、Topk成对返回；53先取得真实idx来源和返回结构。

### 阶段4：P05，完成边界分支和融合步骤

计划累计涉及34个条件。重点是：

- epsilon参数解释。
- Common清理前状态。
- Histogram旧分支。
- 52-A5的真实DP区域和融合前中间值。

对于52-A5，规则必须使用实际融合前值P、乘数Z和DP区域R：

$$
Y_{\mathrm{bad}}[R]=P[R]
$$

其他区域保留健康融合结果，即`Y_bad[非R]=Y_healthy[非R]`。不能通过`Y/Z`反推P，也不能固定污染比例。`Z=1`或`P=0`时可能没有实质变化，需要如实记录。Add分支另定配方。

### 阶段5：完成其余P与特殊路径

沿既定顺序推进P06、P01、P08、P10、P13、P09、P07、P12、P15。

- P10需要重复实验支持跨次变化。
- P13单独统计请求失败和恢复。
- P15在图元数据环境验收。
- 03、24、36持续补证，取得明确后果后再分派主责P。

当前主责P规划合计涉及52/55个条件；03、24、36保留待定。P11、P14保留在P01—P15体系中，目前没有主责代表，不据此新增实施覆盖。

### 阶段6：真实业务与运行模式验收

单算子通过后，接入真实vLLM eager，再验证探针、编译、图回放和多rank。

工作量按实际新增内容估计：

- 新核心逻辑。
- PH特定规则。
- 运行时适配器。
- 状态采集与校准。
- native构建及平台差异。
- 各模式的验收。

当前不宜用57行表格直接换算开发天数。
